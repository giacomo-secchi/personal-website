## Repository overview

This is a monorepo of two WordPress block (full-site-editing) themes plus shared
must-use plugins, deployed together to a single Cloudways-hosted WordPress site:

- `themes/personal-theme` — the main portfolio/landing site.
- `themes/resume` — a standalone CV/résumé theme (serves `cv.giacomosecchi.com`;
  see [themes/resume/README.md](themes/resume/README.md) for its full documentation).
- `mu-plugins/` — must-use plugins shared by both themes (admin settings, user
  profile fields, block bindings sources).

Each theme is built independently (separate `package.json`/`webpack.config.js`) but
both are built and deployed together by the same CI workflow.

## Local development

The site is developed against [`wp-env`](https://developer.wordpress.org/block-editor/reference-guides/packages/packages-env/)
(see `.wp-env.json`), which mounts `./themes/personal-theme`, `./themes/resume` and
`./mu-plugins` straight from the repo into the Docker container — no manual linking
into a `wp-content/` folder is needed:

```sh
npx @wordpress/env start   # first run also activates the theme/plugins and runs a
                            # one-off production build for both themes, see lifecycleScripts
```

Per-theme build commands (run from inside `themes/personal-theme` or `themes/resume`):

```sh
npm ci
npm run start   # wp-scripts watch build — run this for active development (live reload)
npm run build   # production build — what `wp-env start` already runs once via lifecycleScripts
```

Both themes wrap `@wordpress/scripts`; `npm run test` is not implemented in either
theme (it just exits with an error) — there is no test suite in this repo.

- `themes/resume` builds `src/` → `build/` (git-ignored) and its webpack config
  additionally copies Bootstrap Icons SVGs into `build/bootstrap-icons/` for the
  Icons API, and `src/fonts`/`src/css` as-is into `build/fonts`/`build/css`.
- `themes/personal-theme` builds `src/` → `build/` (git-ignored) and its
  webpack config additionally copies `src/fonts` and `src/images` into
  the output, and auto-discovers entry points via `@writepoetry/webpack-utils`.

Required plugin dependency for content editing: Advanced Custom Fields (Pro). Other
integrations (Yoast SEO, TranslatePress, Tabor Dark Mode Toggle block) are optional
and feature-guarded — each theme's `functions.php` only `require`s the matching
`inc/*.php` file when the relevant plugin class/function exists.

ACF Pro is a licensed plugin and isn't downloadable from wordpress.org, so it isn't
listed in `.wp-env.json`. Instead, map your own local copy (or an ACF-account direct
download URL with your license key embedded) via `mappings` in a local
`.wp-env.override.json` (git-ignored, takes precedence over `.wp-env.json`, and its
`mappings`/`config` keys are merged rather than replacing the base file):
```json
{
  "mappings": {
    "wp-content/plugins/advanced-custom-fields-pro": "/absolute/path/to/advanced-custom-fields-pro"
  }
}
```

## Architecture

### Block registration pattern differs between the two themes

- `themes/resume` uses the newer metadata-collection API:
  `wp_register_block_types_from_metadata_collection( __DIR__ . '/build', __DIR__ . '/build/blocks-manifest.php' )`,
  generated by `wp-scripts build --blocks-manifest`. Blocks live in `src/<block>/`
  and build to `build/<block>/`.
- `themes/personal-theme` auto-registers every `block.json` found under
  `build/blocks/*/block.json` (the built output of `src/blocks/*`) via
  `register_block_type()` in a glob loop (`inc/register-blocks.php`).

### `themes/resume` — content model and view system

Content is modelled entirely in ACF (local JSON in `acf-json/`, auto-loaded): post
types `experience`, `internship`, `education`, `project`, `event_presentation`,
`publication`, plus a *Resume Settings* options page for profile/contact fields and
skills/languages repeaters.

Three custom dynamic blocks (namespaced `resume/`, block API v3, all with `render.php`):

| Block | Purpose |
|---|---|
| `resume/resume-section` | One résumé section (`<dl>`) built from a CPT, entries ordered by menu order then real-world date. |
| `resume/list-section` | Renders a repeater field from the options page (email/phone/URL rows → the right link markup). |
| `resume/tab-switch` | The CV/Resume tablist; writes the active view into the `resume/tabs` Interactivity store and the `?view=` URL param. |

The CV/Resume toggle is built on the **WordPress Interactivity API**: each résumé
entry declares which view(s) it belongs to, the active view is driven by `?view=`
(kept in sync via `history.pushState()`, no reload), and views are defined once in
`inc/resume-views.php` via the `resume_views` filter — **order matters**, the first
registered view is the default shown when no `?view=` is present.

Icons (`inc/icons.php`) register the Bootstrap Icons collection with the WP 7.1+
Icons API and expose `resume_get_icon_choices()` to the block editor as
`window.resumeIconChoices` (via `enqueue_block_editor_assets`), backing the
"Section icon" picker used by `resume-section` and `list-section`. This replaced an
earlier Bootstrap-only implementation — the choices function accepts a collection
filter so more icon sets can be added later.

Structured data has two layers: JSON-LD (`inc/schema-jsonld.php`, extends Yoast's
`Person` schema graph from the CPTs) and semantic HTML (`<dl>`-based microdata résumé
markup in each block's `render.php`).

`inc/pdf.php` (a DocRaptor-based PDF export) exists but is currently disabled — its
`require` is commented out in `functions.php`.

### `themes/personal-theme` — portfolio and block bindings

Uses Jetpack's `jetpack-portfolio` CPT (conditionally, only `if ( class_exists( 'Jetpack' ) )`)
with dedicated templates (`templates/*jetpack-portfolio*.html`).

`inc/register-block-binding.php` registers three custom block bindings sources
(`personal-website/user-full-name`, `personal-website/job-position`,
`personal-website/user-email`) that pull from the WordPress user designated as the
"Portfolio Administrator" — a site option (`personal_website_user_login`, General
Settings) resolved by `get_personal_website_admin_user()` in
`mu-plugins/project-custom-functions.php`, which also adds the custom user-profile
fields (career start year, job role, public email, experience phrase) these bindings
read from.

Custom blocks live in `src/blocks/*` (overlay, popup, portfolio-button,
portfolio-filter, portfolio-gallery, portfolio-query) and build to `build/blocks/*`.

## CI/CD

`.github/workflows/main.yml` runs on every push to `main`:

1. **build** — Node 22; for each of `themes/personal-theme` and `themes/resume`:
   `npm ci && npm run build --if-present`. Uploads `themes/` + `mu-plugins/` as the
   `deploy-payload` artifact, excluding `node_modules`, `src/`, source maps, and
   VCS files.
2. **deploy** — ships the payload to Cloudways over SFTP via the reusable
   `WritePoetry/reusable-workflows` deploy workflow.

Since `build/` is git-ignored for both themes, CI's build step is what actually
produces the compiled output that ends up on the server — there is no committed
build output to fall back on.
